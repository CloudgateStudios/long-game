# Long Game — Project Brief

App name: **Long Game** (Xcode project and target name `LongGame`). A personal, single-user app for iPhone, iPad and Mac that
holds a training plan, reads completed workouts and recovery data from Apple Health, checks
what was done against what was planned, and uses a cloud LLM "coach" to review progress and
propose plan changes toward the goals the athlete sets.

This document is the starting brief for Claude Code. Build it milestone by milestone
(section 10). Where this brief says **verify**, check current Apple or Anthropic docs before
relying on it.

---

## 1. Product summary

Three pillars, in priority order:

1. **Plan** — create a training plan toward a goal, either by hand or generated by the coach
   at the start. View and edit it on a calendar.
2. **Track** — read workouts from Apple Health, match them to planned sessions, and show
   whether each session was done, partly done, missed, or unplanned.
3. **Coach** — review what has happened (compliance, training load, recovery signals) and
   suggest specific changes to upcoming sessions. The athlete accepts or rejects each suggestion.

Non-goals for v1: recording workouts, writing to Apple Health, social features, multiple
users, a web version, App Store distribution, pushing workouts to Apple Watch.

## 2. Decisions already made

| Decision | Choice |
|---|---|
| Users | One athlete per install. No accounts, no sign-in. |
| Data source | Apple Health (HealthKit), read-only. |
| Storage and sync | SwiftData backed by CloudKit **private** database in the athlete's own iCloud account. |
| Backend | None. No server of ours, ever. |
| AI | Cloud model (Claude API), called directly from the app, plus a no-key "copy for Claude" export (section 8). |
| Sports | Triathlon (swim, bike, run) is first-class. Everything else is logged and counted but not deeply modelled. |
| Workout sources | Mostly Apple Watch, plus bike computers and other devices, all via Apple Health. |
| Goals | The athlete sets one or more goals (an event, a fitness target) and wants a training plan toward them. The app starts with none. |
| Coach cadence | Weekly review plus on demand. |
| Strength | v1: strength sessions are planned and tracked as sessions with free-text notes. Structured exercises and sets are v2. |
| GPS routes | Not requested. |
| Third-party SDKs | None (no analytics, no crash reporting). |
| Web | Out of scope. |

## 3. Platforms and tech stack

- One SwiftUI multiplatform Xcode project: iOS, iPadOS, macOS targets sharing nearly all code.
- Target the current major OS releases only; no back-deployment needed.
- Swift 6, strict concurrency. SwiftData for persistence. Swift Charts for graphs.
- Swift Testing for unit tests.
- No third-party dependencies unless there is a strong reason; ask first.

**Device roles**

- **iPhone is the ingest device.** It reads HealthKit, computes derived records, and writes
  them to SwiftData. CloudKit carries them to the other devices.
- **iPad and Mac are viewers and editors.** They show the plan, compliance and coach reviews
  from synced data, can edit the plan, and can run the coach. They do not read HealthKit.
  (**Verify:** HealthKit availability on iPadOS and macOS. If iPad has the full health store,
  it may also ingest, but de-duplicate on the HealthKit UUID.)

## 4. Architecture

```
HealthKit (iPhone)
   │  read-only
   ▼
HealthIngest ──► Analysis (pure Swift) ──► SwiftData store ◄──► CloudKit private DB ◄──► iPad / Mac
                                               │
                                               ▼
                                     CoachPayloadBuilder ──► Claude API ──► CoachReview + Suggestions
```

Module layout (local Swift packages or groups):

- `Models` — SwiftData `@Model` types.
- `HealthIngest` — everything that touches HealthKit, behind a `HealthDataSource` protocol
  so the rest of the app never imports HealthKit.
- `Analysis` — pure Swift, no framework imports: zones, training load, baselines, plan
  matching, compliance. This is where most unit tests live.
- `Coach` — payload building, API client, response parsing, suggestion application.
- `App` — SwiftUI views and navigation.

`HealthDataSource` must have a **fixture implementation** that loads sample workouts and
daily metrics from bundled JSON. The simulator has no real health data, so previews, tests
and simulator runs all use the fixture.

## 5. HealthKit read permissions

Read-only. Request no write (share) types.

**Core**
- `HKWorkoutType` (includes sport, duration, distance, energy, effort score)
- `heartRate`
- `restingHeartRate`
- `heartRateVariabilitySDNN`
- `sleepAnalysis`

**Recommended**
- `vo2Max`
- `heartRateRecoveryOneMinute`
- `respiratoryRate`
- `activeEnergyBurned`
- `stepCount`
- `bodyMass`

**Profile characteristics**
- `dateOfBirth`, `biologicalSex`, `height`

**Sport-specific** (all three requested by default, since the plan is triathlon-based)
- Running: `distanceWalkingRunning`, `runningSpeed`, `runningPower`
- Cycling: `distanceCycling`, `cyclingPower`, `cyclingCadence`, `cyclingFunctionalThresholdPower`
- Swimming: `distanceSwimming`, `swimmingStrokeCount`

**Never request:** `HKWorkoutRoute`, ECG, clinical records, medications, blood pressure,
glucose, nutrition, reproductive health, state of mind, audio exposure.

Implementation notes:
- HealthKit does not reveal whether a read permission was denied; a denied type just returns
  no data. Every signal outside Core must be optional in analysis and in the UI.
- Use `HKAnchoredObjectQuery` for incremental sync and `HKObserverQuery` with background
  delivery for new workouts. Persist anchors.
- Identify workouts by HealthKit UUID to avoid duplicates. Handle deletions.
- Workouts from third-party sources may lack heart-rate samples. Fall back to duration-based
  load and mark the record as lower confidence.
- First launch: backfill the last 90 days.
- **Duplicates across devices.** The same ride may be recorded by both the Apple Watch and
  a bike computer. Treat two workouts of the same sport whose time ranges overlap by more than
  ~70% as one session: keep both records, mark one as primary (prefer the one with power
  for cycling, otherwise the one with HR samples), and count only the primary toward load
  and matching. Allow a manual override.
- **Multisport workouts.** A triathlon or brick recorded as one `swimBikeRun` workout
  contains per-leg `HKWorkoutActivity` entries. Split it into one CompletedWorkout per leg,
  linked by a shared session ID.

### FIT file import (fallback source)

If Apple Health turns out to hold only a summary for rides from a bike computer (no HR or power samples),
the app can import the ride's `.fit` file instead. Build this only if the M2 check on a
real ride shows the gap.

- Entry points: share sheet / "Open in" from the bike computer's app, and a file picker. Register
  `.fit` as an imported document type. Works on iPhone, iPad and Mac.
- Put it behind the same seam as HealthKit: a `FITWorkoutSource` that produces the same
  CompletedWorkout records, with source marked as FIT import.
- Read from the file: sport, start, duration, distance, HR, power, cadence, speed, laps.
  **Discard GPS position records while parsing** and do not keep the original file after
  import, so the no-location rule still holds.
- De-duplicate against HealthKit using the same overlap rule. When a FIT import and a
  HealthKit workout are the same session, the FIT record becomes primary and the HealthKit
  one is kept as the duplicate.
- Parsing: FIT is a binary format, so use Garmin's official FIT SDK for Swift rather than
  writing a parser. This is the one approved exception to the no-dependencies rule;
  **verify** its licence and that it makes no network calls.
- Test with a synthetic `.fit` fixture, not a real ride.

### Sport mapping

Map `HKWorkoutActivityType` to an app-level `Sport`:

- **Endurance (plannable in detail, sport-specific metrics):** swim, bike, run.
- **Strength:** traditional and functional strength training, core training.
- **Other (logged, counted toward load, shown in the log):** walk, hike, curling, and
  anything else, kept with its original activity name.

Any sport can appear in the plan, but plan generation and coach suggestions focus on
swim, bike, run and supporting strength. "Other" activities matter to the coach as extra
fatigue (for example a long hike the day before a key run).

## 6. Data model (SwiftData, CloudKit-compatible)

CloudKit rules to follow: every property optional or defaulted, no unique constraints, all
relationships optional with inverses. Mark health-derived fields and anything the athlete
or the coach wrote with `@Attribute(.allowsCloudEncryption)`.

The Production schema only accepts additions: a deployed field can never be removed,
renamed, retyped or have its encryption changed. The models are versioned (`SchemaV1`).

Calendar days (a session's day, a night's metrics, plan and phase ranges, a goal's date) are
stored as `CalendarDay` stamps, midnight UTC of that year, month and day, and read through
a `date` accessor. A day therefore stays the same day when the device changes time zone.

- **AthleteProfile** — age source (DOB), sex, height, weight, max HR, resting HR baseline,
  HR zones (auto-derived, manually overridable), threshold values per sport (FTP, threshold
  pace), enabled sports, weekly availability (days and hours), notes for the coach
  (injuries, constraints, preferences).
- **Goal** — title, type (event / fitness / body), event sport and distance, target date,
  target metric (for example finish time), priority (A / B / C), status. Several goals can
  be active at once; the plan is built around the A goal and fits B and C events in.
  No seed data: the app starts with no goals.
- **TrainingPlan** — name, start and end dates, linked goal, phases (base, build, peak,
  taper, recovery) with date ranges, origin (manual / generated).
- **PlannedWorkout** — date, sport, session type (easy, long, tempo, intervals, strength,
  rest…), target duration, target distance, target intensity (zone or description),
  free-text instructions, status, link to matched CompletedWorkout, order within the day,
  and a brick ID shared by sessions done back to back. Strength sessions use
  the free-text field for exercises and sets in v1; leave room for a structured
  `StrengthSet` child model in v2 without a migration headache.
- **CompletedWorkout** — HealthKit UUID, source name, sport, original activity name,
  session ID (multisport legs), primary/duplicate flag, start, duration, distance,
  active energy, avg and max HR, seconds in each zone, avg power and cadence where
  available, effort score, computed load, confidence flag, and the athlete's own feedback
  (perceived effort 1–10, how it felt, notes).
- **ThresholdSnapshot** — the zones, FTP and threshold paces in force from a given day.
  Written whenever they change, so each workout is scored against the numbers of its day.
- **DailyMetrics** — date, resting HR, HRV, sleep duration, time in sleep stages,
  respiratory rate, steps, active energy, VO2 max, body mass.
- **CoachReview** — date, period covered, trigger (weekly / on-demand / plan generation),
  the exact payload sent (stored as JSON), model used, the narrative response.
- **PlanSuggestion** — parent review, target PlannedWorkout (or a new one), proposed change,
  rationale, status (pending / accepted / rejected).

## 7. Analysis rules (deterministic, unit-tested)

- **Zones** — five HR zones from max HR (or heart-rate reserve when resting HR is known).
  Manual override wins.
- **Workout load** — zone-weighted minutes (TRIMP-style). Fallback when no HR:
  duration × default intensity for the session type.
- **Load by sport** — keep total load and per-sport load (swim, bike, run, strength,
  other) so the coach can see balance across disciplines. Prefer power-based load for
  cycling when power and FTP are available.
- **Load trend** — 7-day acute load, 28-day chronic load, and their ratio. Flag ratios
  outside roughly 0.8–1.3.
- **Recovery baselines** — 28-day rolling mean and standard deviation for HRV, resting HR
  and sleep duration. Flag days more than one standard deviation on the wrong side.
- **Plan matching** — match a CompletedWorkout to a PlannedWorkout of the same sport on the
  same day; if none, allow ±1 day. One-to-one. Unmatched completed workouts are
  "unplanned"; unmatched planned workouts in the past are "missed". Manual re-match and
  un-match must be possible.
- **Compliance** — per session: done (80–120% of target duration or distance), partial
  (50–80%), overdone (>120%), missed. Per week: percent of planned sessions done and
  percent of planned load achieved.

Keep the thresholds in one constants file so they are easy to tune.

## 8. Coach

**When it runs**
- On demand ("Review my training").
- Weekly review (prompted by a local notification; runs when the app is opened from it).
- Plan generation at the start, or regeneration from a given date.

**What is sent** — built by `CoachPayloadBuilder`, as compact JSON:
- Profile: age (not date of birth), sex, height, weight, zones, thresholds, availability,
  coach notes.
- Goals.
- Plan: phases, the last 4 weeks and next 2–4 weeks of planned sessions.
- Completed workouts for the last 4 weeks with match and compliance status.
- Daily metrics for the last 28 days plus baselines and flags.
- Load trend.
- Previous review summary and which suggestions were accepted or rejected.

Send structured summaries and per-workout records, not raw sample streams. That is both
smaller and gives better answers. Never send names, the DOB itself, device identifiers,
locations, or source-app names.

**What comes back** — force a structured response (tool use / JSON schema):
- `assessment`: short narrative of how training is going.
- `flags`: concerns (fatigue, missed key sessions, ramping too fast).
- `suggestions[]`: each one targets a specific planned session by ID (or proposes a new
  one) with action (modify / move / remove / add), the new values, and a rationale.

**Rules**
- Suggestions are never applied automatically. Each is shown as a before/after diff with
  Accept and Reject.
- Every review stores the exact payload sent; a "What was sent" screen shows it.
- The coach prompt states it is a training assistant, not a medical service, and should
  recommend seeing a professional for pain, illness or abnormal readings rather than
  training through them.
- Follow-up chat on a review is a stretch goal, not v1.

**Two ways to run a review**

1. **In-app (API key).** The app calls the Claude API and gets structured suggestions back
   with accept/reject. This is the full experience.
2. **Copy for Claude (no key).** The app puts the same payload plus the coach prompt on the
   clipboard or share sheet, to paste into the Claude app under an existing subscription.
   The reply is read there; suggestions are applied to the plan by hand. Build this in M5
   alongside the in-app path, since it reuses the payload builder and works before any key
   is set up.

A Claude subscription cannot be used as the credential for in-app API calls; the API is
billed separately.

**API details**
- Call the Claude Messages API over `URLSession` from the device. Default model:
  `claude-opus-5-5`, selectable in settings. **Verify** current model IDs, structured
  output options and prompt caching in the Anthropic docs before implementing.
- API key is entered once in settings and stored in the Keychain (iCloud Keychain
  synchronizable so the Mac and iPad get it). Never hard-code it, never commit it, never
  store it in SwiftData or CloudKit.
- Stream the narrative; handle offline, timeout and malformed-response cases with a clear
  retry.

## 9. Privacy and security rules (apply to every change)

1. Health data lives only in HealthKit, the local SwiftData store, and the athlete's CloudKit private
   database.
2. The only outbound network call that carries health-derived data is the coach request to
   the Claude API.
3. No third-party SDKs. No analytics. No remote logging.
4. Never log health values, payloads or the API key, including in debug builds.
5. Local store uses complete file protection.
6. HealthKit access is read-only and limited to section 5.
7. Fixture data in the repo must be synthetic, never exported from anyone's real Health data.

Turning on iCloud Advanced Data Protection on the account makes CloudKit data end-to-end
encrypted.

## 10. Milestones

Each milestone should build, run in the simulator on fixture data, and have passing tests
before moving on.

- **M0 — Skeleton.** Multiplatform project, modules, SwiftData models, CloudKit sync
  working between two devices, fixture `HealthDataSource`, tab/sidebar navigation shell.
- **M1 — Manual plan.** Create goal and plan; add, edit, move, delete planned workouts;
  week and month calendar views.
- **M2 — Health ingest.** HealthKit authorization flow, 90-day backfill, incremental and
  background sync, CompletedWorkout and DailyMetrics populated, profile from
  characteristics.
- **M2b — FIT import (only if needed).** If a real bike-computer ride arrives in Apple Health
  without HR or power samples, add `.fit` import as described in section 5.
- **M3 — Matching and compliance.** Analysis module with tests; plan view shows status per
  session; weekly compliance summary; manual re-match.
- **M4 — Trends.** Load and recovery calculations with tests; dashboard with charts and
  flags.
- **M5 — Coach review.** Settings for API key and model; payload builder; structured
  review; suggestion diffs with accept/reject; "What was sent" screen; review history.
- **M6 — Plan generation.** Onboarding flow: goal, availability, current fitness from
  history → generated plan shown as a draft to edit and accept.
- **M7 — Polish.** iPad and Mac layouts, weekly review notification, empty and error
  states, accessibility pass.
